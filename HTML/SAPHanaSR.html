NAME

SAPHanaSR - スケールアップセットアップにおけるSAP HANAシステムレプリケーションの自動化。

DESCRIPTION

Overview

このマニュアルページ SAPHanaSR には、スケールアップ設定における SAP HANA システムレプリケーション（SR）の自動化の設定と管理に関する情報が記載されています。スケールアウトについては、SAPHanaSR-ScaleOut(7) を参照し、SAPHanaSR-angi(7) も参照してください。

システムレプリケーションは、データベースの障害を補うために、あるサイトから別のサイトへデータベースデータを複製するのに役立ちます。この動作モードでは、内部のSAP HANA高可用性（HA）メカニズムとLinuxクラスタが連携する必要があります。

SAPHanaController RAは、SAP HANAデータベースインスタンスの実際のチェックを実行し、マルチステートリソースとして構成されます。2つのSAP HANAインスタンスを管理することは、リソースエージェントがインスタンスの起動/停止を制御することを意味します。さらにリソースエージェントは、ランドスケープホスト構成レベルでSAP HANAデータベースを監視することができます。この監視のために、リソースエージェントはSAPが提供するインターフェースに依存しています。HANAランドスケープのステータスが 「ERROR 」でない限り、Linuxクラスタは動作しません。Linuxクラスタの主な目的は、他のサイトへのテイクオーバーを処理することです。HANAのランドスケープステータスが、HANAが障害から回復できないことを示し、レプリケーションが同期している場合にのみ、Linuxは動作します。

リソースエージェントの重要なタスクは、2つのSAP HANAデータベースの同期状態をチェックすることです。同期が 「SOK 」でない場合、プライマリに障害が発生しても、クラスタはセカンダリ側へのテイクオーバーを回避します。これはデータの一貫性を向上させるためです。

リソースエージェントの他に、このパッケージにはHADRプロバイダーのフックスクリプトが含まれている。このフックスクリプトは、特定のイベント時にHANAから呼び出されます。重要なイベントの1つは、システムのレプリケーションが失われたときです。関連するフックスクリプトは、次のRAモニターを待たずに、直ちにHAクラスタに通知します。これにより、コーナーケースでもデータの一貫性が保証されます。フックスクリプトのもう1つの使用例は、HANAリソースがメンテナンスモードの場合に手動テイクオーバーを許可し、それ以外の場合は手動テイクオーバーをブロックすることです。これにより、二重プライマリ状況を防ぐことができます。

Scenarios

上記の概要の意味を説明するために、いくつかの重要な状況を以下に説明する。これはすべての状況を完全に説明するものではない。

1. Site takeover after primary has failed
これがHANA SRオートメーションの基本的な使用例です。
1. site_A is primary, site_B is secondary - they are in sync.
2. site_A crashes.
3. site_Bがテイクオーバーを行い、新しいプライマリとして実行される。Linuxクラスタは、他のアクションが開始される前に、常にsite_Bのノードがシャットオフされていることを確認する。

2. 二重プライマリーの防止
クラスタが他のサイトについて何も知らない場合は、絶対にプライマリを開始してはなりません。最初のクラスタ起動時に、クラスタは、システムレプリケーションステータス（SOK）および最後のプライマリタイムスタンプ（LPT）を含む、有効なHANAシステムレプリケーション設定を検出する必要があります。これはデータの整合性を確保するために必要です。

Tその合理的根拠を次のシナリオに示す：
1. site_A is primary, site_B is secondary - they are in sync.
2. site_A crashes （HANA がプライマリのままであることに注意してください）
3. site_Bがテイクオーバーを行い、新しいプライマリとして実行される。
4. ＊本番稼動によりノード2でデータが変更される＊
5. 管理者はまた、site_B上のクラスタを停止します（現在、内部的に2つのHANAがあり、両方はダウンとプライマリにマークされています）。
6. 管理者がsite_Aのクラスタを再起動したらどうなるだろうか？
6.1 site_Aは、site_Bの最初のフェンシング時間を待った後、自身のCIBを取る。
6.2 自分自身が(cold)状態だったプライマリであることと、セカンダリが存在することを認識する。
6.3 ステップ1.->2.（クラッシュ）の時点からHANAを起動するため、その間に変更されたデータはすべて失われます。
このため、Linuxクラスタでは再起動を禁止する必要がある。

SAP HANA SRとLinuxクラスタの両方を完全に機能する状態に戻すには、2つのオプションがあります：
a) 管理者が両ノードを再び起動する
b) site_Bがまだダウンしている場合、管理者は手動でsite_Aのプライマリを起動する。
Linuxクラスタはこの管理者の決定に従う。どちらの場合も、管理者はできるだけ早くセカンダリを登録して起動する必要があります。これにより、DATABASE STUCKの結果としてのログ・パーティションがフルになるのを避けることができます。

3. サイト障害およびTakeover後にセカンダリとして自動登録
クラスタは、以前のプライマリデータベースを自動的にセカンダリとして登録するように設定できます。このオプションを設定すると、リソースエージェントはクラスタ/リソースの起動時に以前のプライマリデータベースをセカンダリとして登録します。

4. テイクオーバーよりローカルでの再起動を優先する
SAPHanaController RA では、プライマリランドスケープに障害が発生した後にセカンダリランドスケープに引き継ぐかどうかを設定できます。別の方法として、プライマリランドスケープに障害が発生した場合に再起動し、ローカルでの再起動が不可能になった場合にのみ引き継ぎを行います。ocf_suse_SAPHanaController(7) も参照してください。
現在の実装では、ランドスケープステータスが1(ERROR)を報告した場合にのみテイクオーバーできます。SAP HANAがまだローカル障害の修復を試みている場合、クラスタはテイクオーバーしません。

Implementation

2つのHANAデータベースシステム（プライマリサイトとセカンダリサイト）は、同じ単一のLinuxクラスタによって管理される。その単一のLinuxクラスタのノード数は通常2台です。

HANAは、それぞれ1つのノードを持つ2つのサイトで構成されている。
注：別のシステムレプリケーション（別名マルチターゲットレプリケーション）を使用して、3つ目のHANAサイトを追加できます。これはクラスタによって許容されます。しかし、この追加ピースはクラスタによって管理されません。そのため、マルチターゲットセットアップでは、AUTOMATED_REGISTER機能はHANAのregister_secondaries_on_takeover機能を必要とします。

全サイトの全ノードに共通のSTONITHメカニズムが設定されています.

プライマリHANAデータベースシステムのIPアドレスはクラスタによって管理されているため、どのネームサーバー候補にアクセスするにも、その単一のIPアドレスのみが必要となります。

Best Practice

* 2つの独立したコロシンク・リングを使用し、少なくとも1つはボンディング・ネットワーク上に置く。その結果、少なくとも3つの物理リンクになる。ユニキャストが望ましい。

* Stonith Block Device (SBD)を使用し、全サイトの全ノードでLUNを共有する。もちろん、ハードウェア・ウォッチドッグも併用する。

* Linuxクラスタ内のすべてのタイムアウトを、特にネットワーク、ストレージ、マルチパスといった基盤インフラのタイムアウトに合わせる。

* 機能テストを行う前に、すべてのノードでOSとLinuxクラスタのインストールを確認する。

* すべての保守手順だけでなく、カバーすべきすべてのシナリオのテストを慎重に定義し、実行し、文書化します。

* クラスター全体のテストを行う前に、LinuxクラスターなしでHANA機能をテストします。

* クラスター全体のテストを行う前に、HANAを使用せずに基本的なLinuxクラスター機能をテストします。

* 気長に。HANAの全体的な状態を検出するには、HANAと構成されている間隔とタイムアウトに応じて、Linuxクラスターに一定の時間が必要です。

* 何かを行う前に、Linuxクラスターのアイドル状態、残っている移行の制約、リソースエラー、およびHANAランドスケープの状態とHANA SRの状態を必ず確認してください。

* HANAプライマリを手動でアクティブ化すると、デュアルプライマリのリスクが生じます。ユーザーはデータの整合性に責任があります。susTkOver.py (7) も参照してください。

REQUIREMENTS

パッケージSAPHanaSR-angiの現在のバージョンでは、スケールアップ機能は次のシナリオとパラメーターに制限されます。

1．システムレプリケーションを使用したHANAスケールアップクラスター。2つのHANAデータベースシステム (プライマリサイトとセカンダリサイト) は、1つのLinuxクラスターで管理されます。この単一のLinuxクラスタのノード数は2です。注意:3ノードのLinuxクラスタは可能ですが、現在のベストプラクティスではカバーされていません。

2．sidadmなどの技術ユーザーとグループは、Linuxシステムでローカルに定義されます。ユーザがリモートサービスによって解決される場合は、ローカルキャッシュが必要です。sidadmの代替ユーザー (su) は、カスタマイズされたアクションやメッセージを使用せずに、信頼性の高い方法で動作する必要があります。サポートされているシェルはbashです。

3．クラスタノード間の厳密な時刻同期 (NTPなど) 。Linuxクラスタのすべてのノードで同じタイムゾーンが設定されています。

4. スケールアップについては、次のSAP HANA SRシナリオがSAPHanaSR-angiパッケージで可能です。SAPHanaSR-angi-scenarios (7) も参照してください。
4.1 performance-optimized (memory preload on secondary)
4.2 cost-optimized (e.g. with QA on secondary)
4.3 multi-tier with HANA 2.0 (replication chaining, third node connected to second one)
4.4 multi-target with HANA 2.0 (star replication, third node connected to primary one)
4.5 single-tenant or multi-tenant (MDC) for all of the above
4.6 multiple independent HANA SR pairs (MCOS) in one cluster
Note: For MCOS, there must be no constraints between HANA SR pairs.

5. 5. Linuxクラスター内の2つのSAP HANAデータベース間で1つのシステムレプリケーションのみ。Linuxクラスター外のHANAデータベースへの最大1つのシステムレプリケーション。下記項目12も参照。

6. レプリケーションモードは、制御レプリケーションの場合はsyncまたはsyncmemです。レプリケーションモードの非同期はサポートされていません。操作モードdelta_datashipping、logreplay、logreplay_readaccessがサポートされています。動作モードはlogreplayです。

7. 両方のSAP HANAデータベースシステムのSAP識別子 (SID) とインスタンス番号 (INO) は同じです。

8. SAP HANAに加えて、SAPホストエージェントをシステムにインストールして開始する必要があります。SystemVスタイルでは、sapinitスクリプトをアクティブにする必要があります。systemdスタイルの場合、サービスsaphostagentとSAP${SID}_${INO}は有効のままにできます。systemdのバージョンについては、OSのドキュメントを参照してください。SAP HANAのバージョンについては、SAPのドキュメントを参照してください。systemdスタイルのhostagentとSystemVスタイルのインスタンスを組み合わせることができます。ただし、1つのLinuxクラスター内のすべてのノードで同じスタイルを使用する必要があります。

9. システム起動時のSAP HANAデータベースシステムの自動起動をオフにする必要があります。

10. RAの監視操作はアクティブである必要があります.

11. susHanaSR.pyまたはsusHanaSrMultiTarget.pyを有効にして、srConnectionChanged() のHA/DRプロバイダーフックを使用することは必須です。

12. スケールアップの場合、現在のリソースエージェントは、HANAバージョン2.0 SPS05 rev.59.04以降のシステムレプリケーションでSAP HANAをサポートします。

13. SAPHanaController RAとその他のリソース間のコロケーション制約は、RAのスコアリングに影響しない場合にのみ許可されます。ロケーションスコアリングは最終的にシステム複製ステータスに依存し、追加の制約によって上書きされてはなりません。したがって、SAPHanaControllerリソースが別のリソースに従うように強制するルールを定義することはできません。

14. HA/DRプロバイダーイベントをCIB属性に書き込むには、Linuxクラスタが稼働している必要があります。現在のHANA SRの状態は、クラスターのメンテナンス後にCIB srHook属性と異なる場合があります。

15. HANAシステムレプリケーションサイトがLinuxクラスターに認識されると、サイトを手動で登録するたびに、正確なサイト名を使用する必要があります。常に1つのサイトのみがプライマリ・レプリケーション・ソースとして構成される

17. HANA機能セカンダリタイムトラベルはサポートされていません。.

18. MDC構成では、HANAデータベースは、すべてのデータベースコンテナーを含む1つのシステムとして扱われます。したがって、クラスターの引き継ぎの決定は、個々のコンテナーの状態とは関係なく、完全な状態に基づいて行われます。

19. 3つ目のHANAサイトがシステムレプリケーションによって接続されている場合、そのHANAは別のSUSE HAクラスターによって制御されません。その3番目のサイトがDRの場合にフォールバックHAクラスタの一部として動作する必要がある場合は、そのHAクラスタをスタンバイにする必要があります。

21. RAM-tmpfs上のSAP HANA Fast Restart機能と永続メモリ上のHANAは、SUSE HAに対して透過的であれば使用できます。

22. SAP HANAホスト名または仮想ホスト名はRFC-952に従う必要があります。

23. SAP HANAサイト名の長さは2文字から32文字です。文字または数字で始まります。後続の文字にはダッシュとアンダースコアを含めることができます。ただし、アンダースコアは避けてください。

24. SAPHanaController RA、SUSE HAクラスタ、およびいくつかのSAPコンポーネントには、読み取り/書き込みアクセスと、Linux/tmpファイルシステムに十分なスペースが必要です。

25. SAP HANA Native Storage Extension (NSE) がサポートされています。重要なのは、この機能によってHANAトポロジやインターフェイスが変更されないことです。ネイティブストレージ拡張とは反対に、HANA拡張ノードはトポロジを変更しているため、現在はサポートされていません。詳細については、SAPのドキュメントを参照してください。

26. Linuxユーザのrootシェルは/bin/bash、または bash と完全に互換性があるもの。

27. Linuxクラスターによって制御されている間は、HANAデータベースに対して手動アクションを実行する必要はありません。すべての管理アクションをクラスタに合わせる必要があります。SAPHanaSR_maintenance_examples (7) も参照ください。
