NAME

SAPHanaController - システムのレプリケーション（スケールアップ）により、2つのSAP HANAデータベース間のテイクオーバーを管理します。

SYNOPSIS

SAPHanaController [start | stop | status | monitor | promote | demote | meta-data | validate-all | methods | usage ]

DESCRIPTION

SAPHanaController は、SAP HANAデータベース用のリソースエージェント（RA）です。OCFプロモータブルクローン構成で、システムレプリケーションを持つSAP HANAデータベースのテイクオーバーを管理します。このマニュアルページでは、SAP HANA のスケールアップシナリオについて説明します。スケールアウトについては、SAPHanaController-scale-out(7) を参照してください。.

システムレプリケーションは、データベースの障害を補うために、あるコンピュータから別のコンピュータにデータベースデータを複製するのに役立ちます。この動作モードでは、内部のSAP HANA高可用性（HA）メカニズムとリソースエージェントが連携する必要があります。SAPHanaController RAは、SAP HANAデータベースインスタンスの実際のチェックを実行し、プロモータ可能なクローンリソースとして構成されます。2つのSAP HANAインスタンスを管理することは、リソースエージェントがインスタンスの起動/停止を制御することを意味します。さらにリソースエージェントは、ランドスケープホスト構成レベルでSAP HANAデータベースを監視することができます。この監視のために、リソースエージェントはSAPが提供するインターフェースに依存しています。

リソースエージェントの3つ目のタスクは、2つのSAP HANAデータベースの同期状態をチェックすることです。同期が 「SOK 」でない場合、プライマリに障害が発生しても、クラスタはセカンダリサイトへのテイクオーバーを回避します。これはデータの一貫性を向上させるためです。

The resource agent uses the following five interfaces provided by SAP:

1. sapcontrol/sapstartsrv
sapcontrol/sapstartsrvインターフェイスは、HANAデータベースインスタンス/システムを起動/停止するために使用されます。

2. landscapeHostConfiguration
このインターフェースはHANAシステム全体を監視するために使用されます。pythonスクリプトの名前はlandscapeHostConfiguration.pyです。landscapeHostConfiguration.pyには、HANAシステムのステータスとノードの役割に関する詳細な出力があります。私たちのモニターでは、全体的なステータスが重要です。この全体的なステータスはスクリプトのリターンコードで報告されます： 0: Internal Fatal, 1: ERROR, 2: WARNING, 3: INFO, 4: OK SAPHanaControllerリソースエージェントは、リターンコード0をFATAL、1をNOT-RUNNING（またはERROR）、リターンコード2+3+4をRUNNINGと解釈します。

3. hdbnsutil
インターフェイスhdbnsutilは、システムレプリケーションの「トポロジー」とSAP HANAデータベースインスタンスの現在の構成（プライマリ/セカンダリ）を確認するために使用されます。このインターフェイスの2つ目のタスクは、システムレプリケーションのテイクオーバー（sr_takeover）を実行したり、以前のプライマリを新しいプライマリに登録（sr_register）したりすることです。

4. systemReplicationStatus / hdbsql
SAP HANA 1.0 SPS 9 以降では、システムレプリケーションをチェックするための python スクリプト 「systemReplicationStatus.py」 が提供されています。SAPHanaSR-angiはhdbsqlの代わりにこのスクリプトを使用します。そのため、SAPHanaSR-angi で最近のバージョンの SAP HANA を管理する場合、hdbsql は使用されません。

5. saphostctrl
インターフェイス saphostctrl は、関数 ListInstances を使用して SAP HANA インスタンスの仮想ホスト名を特定します。

クラスタの構成をできるだけ簡単にするために、追加のSAPHanaTopologyリソースエージェントはSAPHanaSRクラスタのすべてのノードで実行され、SAP HANAシステムのレプリケーションのステータスと構成に関する情報を収集します。SAPHanaTopology RA は、通常の（ステートレス）クローンとして設計されています。

Please see also the REQUIREMENTS section below and manual page SAPHanaSR-angi-scenarios(7).

SUPPORTED PARAMETERS


This resource agent supports the following parameters:

SID

SAP System Identifier. Has to be same on both instances. Example "SID=SLE".

InstanceNumber

Number of the SAP HANA database. Has to be same on both instances. For system replication also Instance Number+1 is blocked. Example "InstanceNumber=00".

DIR_EXECUTABLE

sapstartsrv および sapcontrol がある完全修飾パス。デフォルトの SAP インストール後に SAP カーネル・ディレクトリの場所を変更した場合は、このパラメータを指定します。
Optional, well known directories will be searched by default.

DIR_PROFILE

SAP START プロファイルがある完全修飾パス。デフォルトの SAP インストール後に SAP プロファイルディレクトリの場所を変更した場合は、このパラメータを指定します。
Optional, well known directories will be searched by default.

HANA_CALL_TIMEOUT

情報を受け取るためにHANAを呼び出す際のタイムアウト時間を定義します。これは例えばlandscapeHostConfiguration.pyのようになります。独自のタイムアウト値を持つHANAへの特定の呼び出しがいくつかあります。例えば、sr_takeoverコマンドはタイムアウトしません(inf)。タイムアウトに達した場合、リターンコードは124になります。HANAコールのタイムアウトを増やす場合は、Linuxクラスタリソースの操作タイムアウトも調整する必要があります。
Optional. Default value: 60.

INSTANCE_PROFILE

SAP HANA インスタンスプロファイルの名前。デフォルトの SAP インストール後に SAP HANA インスタンスプロファイルの名前を変更した場合は、このパラメータを指定します
Optional, well known directories will be searched by default.

PREFER_SITE_TAKEOVER

RAが、プライマリ・サイトをローカルで再起動する代わりに、セカンダリ・データベースへのテイクオーバーを優先するかどうかを定義する。 Example: "PREFER_SITE_TAKEOVER=true".
Optional. Default value: false.

DUPLICATE_PRIMARY_TIMEOUT

デュアルプライマリ状態が発生した場合に、2つのプライマリ・タイムスタンプ(LPT)の間に必要な時間差。両方のノードの最後のプライマリタイムスタンプの差がDUPLICATE_PRIMARY_TIMEOUTより小さい場合、クラスタは1つまたは両方のインスタンスを 「WAITING 」ステータスに保持します。これは管理者に乗っ取りに対応するチャンスを与えるためです。注意: DUPLICATE_PRIMARY_TIMEOUTが経過した後にクラスタがどのように処理を進めるかは、パラメータAUTOMATED_REGISTERに依存します。以下の例のセクションも参照してください。
Optional. Default value: 7200.

AUTOMATED_REGISTER

DUPLICATE_PRIMARY_TIMEOUTが期限切れの場合、以前のプライマリ・インスタンスをクラスタ/リソースの開始時にリソース・エージェントによって自動的に登録するかどうかを定義します。 Example: "AUTOMATED_REGISTER=true".
Default value: false.

SAPHanaFilter

古いパラメータです。今後使用しないでください。このリソースエージェントパラメータはクラスタプロパティ "hana_${sid}_glob_filter" に置き換えられました。

SUPPORTED PROPERTIES


hana_${sid}_glob_filter

Global cluster property hana_${sid}_glob_filter . このプロパティは、サポートエンジニアから要求された場合にのみ設定すべきである。通常の操作では、デフォルトで十分です。

SUPPORTED ACTIONS


This resource agent supports the following actions (operations):

start

HANAインスタンスを起動するか、「クローンインスタンス」を待機状態にします。推奨される最小タイムアウト： 3600.

stop

HANAインスタンスを停止します。適切な値は、データベースサイズなどの要因に依存します。HANAデータベースの内部タイムアウトが高速シャットダウンのために調整されている場合、RAタイムアウトは減少する可能性があります。推奨される最小タイムアウト： 600.

promote

セカンダリーのテイクオーバーか、プライマリーのジャストナッシングを実行する。推奨される最小タイムアウト： 320..

demote

ほとんど何もせず、インスタンスを降格としてマークするだけです。推奨される最小タイムアウト： 320.

status

Reports whether the HANA instance is running. Suggested minimum timeout: 60.

monitor (promoted role)

HANAインスタンスがレプリケーションプライマリモードで動作しているかどうかを報告します。また、システムのレプリケーションステータスもチェックします。推奨される最小タイムアウト： 700. 推奨間隔：60

monitor (demoted role)

HANAインスタンスがレプリケーションセカンダリモードで動作しているかどうかを報告します。また、システムのレプリケーションステータスもチェックします。スレーブロールの監視間隔は昇格ロールとは異なる必要があります。推奨される最小タイムアウト： 700. 推奨間隔：61。

validate-all

Reports whether the parameters are valid. Suggested minimum timeout: 5.

meta-data

Retrieves resource agent metadata (internal use only). Suggested minimum timeout: 5.

methods

Suggested minimum timeout: 5.

RETURN CODES

リターンコードはOCFクラスターフレームワークによって定義されている。OCFの定義は後述のウェブサイトを参照されたい。
さらに、ログエントリが書き込まれ、"SAPHanaCon.*RA.*rc=[1-7,9]" のようなパターンを使用してエラーをスキャンできます。通常の操作は、"SAPHanaCon.*RA.*rc=0" で見つかるかもしれない。

EXAMPLES

* 以下は、パフォーマンス最適化シナリオにおける SAPHanaController マルチステートリソースの構成例です。

また、これを実行するには SAPHanaTopology クローンリソースが必要です。

primitive rsc_SAPHanaCon_SLE_HDB00 ocf:suse:SAPHanaController \
op start interval="0" timeout="3600" \
op stop interval="0" timeout="3600" \
op promote interval="0" timeout="900" \
op demote interval="0" timeout="320" \
op monitor interval="60" role="Promoted" timeout="700" \
op monitor interval="61" role="Started" timeout="700" \
params SID="SLE" InstanceNumber="00" PREFER_SITE_TAKEOVER="true" \
DUPLICATE_PRIMARY_TIMEOUT="7200" AUTOMATED_REGISTER="false"

clone mst_SAPHanaCon_SLE_HDB00 rsc_SAPHanaCon_SLE_HDB00 \
meta clone-max="2" clone-node-max="1" interleave="true" promotable="true"

* 以下は、コスト最適化シナリオにおける 2 つの SAPHanaController リソースの構成例です。

最初のSAP HANAリソースは、SAPHanaController RAによって管理される、システムレプリケーション（PRDなど）を備えた本番用HANAのマルチステートペアです。2番目のSAP HANAは、同じノード上で生産HANAセカンダリと共に稼働する単一のテストHANA（TSTなど）です。この2番目のシングルHANAは、SAPInstance RAによってプリミティブリソースとして管理されます。もちろん、これを実現するにはSAPHanaTopologyクローンリソースが必要です。また、sr_takeoverの場合にセカンダリHANAのメモリを調整するためのHANA HA/DRフックスクリプトを準備する必要があります。 マニュアルページのsusCostOpt.py(7)と以下のURLを参照してください。最後に、SAPHanaControllerプライマリはプライオリティフェンシングを可能にするためにプライオリティを取得します。マニュアルページ SAPHanaSR_basic_cluster(7) を参照してください。

primitive rsc_SAPHanaCon_PRD_HDB10 ocf:suse:SAPHanaController \
op start interval="0" timeout="3600" \
op stop interval="0" timeout="3600" \
op promote interval="0" timeout="900" \
op demote interval="0" timeout="320" \
op monitor interval="60" role="Promoted" timeout="700" \
op monitor interval="61" role="Started" timeout="700" \
params SID="PRD" InstanceNumber="10" PREFER_SITE_TAKEOVER="false" \
DUPLICATE_PRIMARY_TIMEOUT="7200" AUTOMATED_REGISTER="false" \
meta priority=100

clone mst_SAPHanaCon_PRD_HDB10 rsc_SAPHanaCon_PRD_HDB10 \
meta clone-max="2" clone-node-max="1 interleave="true" promotable="true"

primitive rsc_SAPInstance_TST_HDB10 ocf:heartbeat:SAPInstance \
params InstanceName="TST_HDB10_node02 \
MONITOR_SERVICES="hdbindexserver|hdbnameserver" \
START_PROFILE="/usr/sap/{sapnpsid}/SYS/profile/TST_HDB10_node02" \
op start interval="0" timeout="600" \
op monitor interval="120" timeout="700" \
op stop interval="0" timeout="300" \

location loc_TST_never_on_node01 rsc_SAPInstance_TST_HDB20_node02 -inf: node01

colocation col_TST_never_with_PRD-ip -inf: rsc_SAPInstance_TST_HDB20_node02:Started \
rsc_ip_PRD_HDB10

order ord_TST_stop_before_PRD-promote inf: rsc_SAPInstance_TST_HDB20_node02:stop \
mst_SAPHanaCon_PRD_HDB10:promote

* HANAプライマリを一方のノードから他方のノードに引き継ぐ。

クラスタが以前のプライマリをセカンダリとしても登録する場合は、AUTOMATED_REGISTER="true"が必要です。テイクオーバーを開始する前に、LinuxクラスタとHANAシステムのレプリケーションのステータスをチェックする必要があります。テイクオーバーは強制マイグレーションとしてのみ開始する必要があります。引き継ぎが終了したら、移行ルールを削除する必要があります。
Note: Older versions of the Linux cluster have used the commands 'migrate' and 'unmigrate' instead of 'move' and 'clear'.

# cs_clusterstate
# SAPHanaSR-showAttr
# crm configure show | grep cli
# crm resource move mst_SAPHanaCon_SLE_HDB10 force
# cs_clusterstate -i
# SAPHanaSR-showAttr
# crm resource clear mst_SAPHanaCon_SLE_HDB10

* 利用可能なノードが1つしかない場合、HANAプライマリを手動で起動します。

これは、クラスタが両方のノードのステータスを検出できなかった場合に必要となる。

1. Start the cluster.
2. クラスタが実行中で、アイドル状態であることを確認する。
3. Become sidadm, and start HANA manually.
4. Wait and check for HANA is running.
5. クラスタがHANAをプライマリに昇格させない場合は、そのノードにIPアドレスを移行するようクラスタに指示します。
6. HANAがクラスタによってプライマリに昇格されるのを待つ。
7. IPアドレスから移行ルールを削除する。
8. You are done, for now.
9. もう一方のノードを戻して、できるだけ早くそのHANAを登録してください。HANAのプライマリだけが長い間残っていると、ログ領域がいっぱいになってしまいます。

* 以下は、デフォルトに設定されたログメッセージのフィルターを示している。

このプロパティは、サポートエンジニアから要求された場合にのみ設定すべきである。通常の操作では、デフォルトで十分です。

property $id="SAPHanaSR" \
hana_SLE_glob_filter="ra-act-dec-lpa"

# grep "SAPHana.*RA.*rc=[1-7,9]" /var/log/messages

Resource is rsc_SAPHanaCon_HA1_HDB00, node is node22. Useful after a failure has been fixed and for testing. See also cluster properties migration-threshold, failure-timeout and SAPHanaController parameter PREFER_SITE_TAKEOVER.

# crm resource failcount rsc_SAPHanaCon_HA1_HDB00 show node22
# crm resource failcount rsc_SAPHanaCon_HA1_HDB00 delete node22

* Check for working NTP service on SLE-HA 15:

# chronyc sources

* プライマリ・ノードが完全にクラッシュした場合に、DUPLICATE_PRIMARY_TIMEOUTと最終プライマリ・タイムスタンプ（LPT）を使用する。

通常、RAが実行中のプライマリを検出する各側で、タイムスタンプがノードのLPT属性に書き込まれる(last primary seen at time: lpt)。タイムスタンプ(「last primary seen at」)がDUPLICATE_PRIMARY_TIMEOUTより小さい場合、RAが自動的に2つのプライマリのうち、どちらが優れているかを決定することはできない。

1. ノードAはプライマリで現在のタイムスタンプを持ち、ノードBはセカンダリでセカンダリマーカーがセットされている：
nodeA: 1479201695
nodeB: 30

2. 今度はノードAがクラッシュし、ノードBが引き継ぐ：
(nodeA: 1479201695)
nodeB: 1479201700

3. 少ししてnodeAがクラスタに復帰した：
nodeA: 1479201695
nodeB: 1479202000
nodeAがプライマリを停止している間、古いタイムスタンプが維持されていることがわかる。NodeBはモニターを実行するたびにタイムスタンプを増やします。

4. さらに時間が経過した後（DUPLICATE_PRIMARY_TIMEOUTパラメータに依存）。
nodeA: 1479201695
nodeB: 1479208895
Now the time stamps differ >= DUPLICATE_PRIMARY_TIMEOUT. アルゴリズムはノードAを 「ルーザー 」と定義し、AUTOMATED_REGISTERに応じてノードAがセカンダリになる。

5. NodeA would be registered:
nodeA: 10
nodeB: 1479208900

6. しばらくしてセカンダリーが同期する
nodeA: 30
nodeB: 1479209100

* DUPLICATE_PRIMARY_TIMEOUTと最終プライマリ・タイムスタンプ（LPT）は、プライマリ・ノードのデータベースがクラッシュしたが、そのノードがまだ生きている場合に使用します。

通常、RAが実行中のプライマリを検出する各側で、タイムスタンプがノードのLPT属性に書き込まれる(last primary seen at time: lpt)。タイムスタンプ(「last primary seen at」)がDUPLICATE_PRIMARY_TIMEOUTより小さい場合、RAが自動的に2つのプライマリのどちらを優先するかを決定することはできない。

1. ノードAはプライマリで現在のタイムスタンプを持ち、ノードBはセカンダリでセカンダリマーカーがセットされている：
nodeA: 1479201695
nodeB: 30

2. ノードAのHANAがクラッシュし、ノードBが引き継ぐ：
nodeA: 1479201695
nodeB: 1479201700

3. クラスタがnodeAでHANAインスタンスを適切に停止したことを確認できたので、AUTOMATED_REGISTERがtrueの場合、古いプライマリを登録候補として*直ちに*マークします：
nodeA: 10
nodeB: 1479201760

4. AUTOMATED_REGISTERパラメータによっては、RAは、以前のプライマリを即座に新しいセカンダリに登録する：
nodeA: 10
nodeB: 1479201820

5. And after a while the secondary gets in sync
nodeA: 30
nodeB: 1479202132
