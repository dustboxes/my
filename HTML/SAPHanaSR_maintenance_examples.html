SAPHanaSR_maintenance_examples

10 Jan 2025

NAME

SAPHanaSR_maintenance_examples - maintenance examples for SAPHanaController.

DESCRIPTION

Maintenance examples for SAPHanaController. Please see ocf_suse_SAPHanaController(7), susHanaSR.py(7), susHanaSrMultiTarget.py(7), susTkOver.py(7), susChkSrv.py(7), SAPHanaSR-manageAttr(8), for more examples and read the REQUIREMENTS section below.

EXAMPLES

* Check status of Linux cluster and HANA system replication pair.

この手順は、クラスターで何かを行う前、および何かを行った後に実行する必要があります。cs_show_saphanasr_status (8) および後述のセクション「要件」も参照してください。

# cs_clusterstate -i
# crm_mon -1r
# crm configure show | grep cli-
# SAPHanaSR-showAttr
# cs_clusterstate -i

* HANAクラスターリソースとシステムレプリケーションの状態を監視します。

これは、管理アクションやクラスタテストを実行する場合に便利です。前述のチェックに代わるものではありません。cs_show_saphanasr_status (8) も参照してください。

# watch -n9 "crm_mon -1r --include=none,nodes,resources,failures;echo;SAPHanaSR-showAttr;cs_clusterstate -i|grep -v '#'"

* 1つのサイトでのHANAデータベースの停止の概要。

この手順は、スケールアップとスケールアウトに有効です。テイクオーバーは行われません。HANAデータベースを停止する必要がある場合は、この手順を使用する必要があります。HANAデータベースの停止は、Linuxクラスターの停止やOSのシャットダウンだけでは実行できません。これは特にスケールアウトシステムに当てはまる。停止する必要があるHANAサイトを事前に定義することをお勧めします。両方のサイトを停止する必要がある場合は、順序を定義するとよいでしょう。最初にプライマリを停止すると、システム複製の同期が維持されます。
停止にかかる時間は、データベースのサイズ、基になるインフラストラクチャのパフォーマンス、SAP HANAのバージョンと構成によって異なります。HANAデータベースのチューニングと停止の詳細については、SAP HANAのドキュメントを参照してください。

1. LinuxクラスターとHANAシステムのレプリケーションペアの状態を確認します。
2. SAPHana または SAPHanaController のマルチステート リソースをメンテナンスに設定します。
3. "sapcontrol -nr -function StopSystem" を使用して、指定されたサイトの HANA データベースを停止します。
4. Checking that HANA is stopped.

注意: HANA データベースを再起動した後は、リソースのメンテナンスを終了することを忘れないでください。

* Linux クラスターを使用して、あるノードから別のノードへの HANA プライマリの管理テイクオーバーを開始します。

この手順はスケールアウトには機能しません。スケールアップ時には、HANAプライマリが停止します。これには時間がかかる場合があります。停止したプライマリを待機したくない場合は、以下の手順でプライマリを一時停止してください。クラスターが以前のプライマリをセカンダリとしても登録する必要がある場合は、AUTOMATED_REGISTER="true" を指定する必要があります。テイクオーバーを開始する前に、LinuxクラスターとHANAシステムレプリケーションのステータスを確認する必要があります。テイクオーバーは、マルチステートSAPHanaControllerリソースの強制移行として開始する必要があります。
機能しないもの: 通常の移行、IP アドレスの移行、プリミティブ SAPHanaController リソースの移行、プライマリ ノードのスタンバイの設定。
プライマリのテイクオーバーが完了したら、移行ルールを削除する必要があります。AUTOMATED_REGISTER="true" が設定されている場合、移行ルールが削除されると、元のプライマリは最終的にセカンダリとして登録されます。

# crm_mon -1r
# SAPHanaSR-showAttr
# crm configure show | grep cli-
# cs_clusterstate -i
# crm resource move mst_SAPHanaCon_SLE_HDB10 force
# cs_clusterstate -i
# SAPHanaSR-showAttr
# crm resource clear mst_SAPHanaCon_SLE_HDB10
# SAPHanaSR-showAttr
# cs_clusterstate -i

注意: Linux クラスターの以前のバージョンでは、「move」の代わりに「migrate」を使用し、「clear」の代わりに「unmigrate」を使用していました。

* SAP ツールを使用して SAP HANA のテイクオーバーを実行します。

ここではスケールアウトの手順を説明します。スケールアップにも適用できます。この手順では、HANAプライマリを停止します。これには時間がかかる場合があります。停止したプライマリを待たずに済むようにするには、以下のプライマリを一時停止する手順を使用してください。HANAデータベース、システムレプリケーション、Linuxクラスタのステータスを確認する必要があります。SAP HANAリソースをメンテナンスモードに設定し、sr_takeoverを実行し、古いプライマリを新しいセカンダリとして登録します。そのため、正しいセカンダリサイト名を使用する必要があります（後述の例を参照）。最後に、SAP HANAリソースをLinuxクラスタに戻します。正しいサイト名の決定については、以下の「要件」セクションと後述の例も参照してください。

1. 両方のノードで実行

# crm_mon -1r
# SAPHanaSR-showAttr
# crm configure show | grep cli-
# cs_clusterstate -i
すべて問題がなければ、続行します。
# crm resource maintenance mst_SAPHanaCon_SLE_HDB10
# crm_mon -1r

2. On the HANA primary master nameserver (e.g. node11)

# su - sleadm
~> sapcontrol -nr 10 -function StopSystem HDB
~> sapcontrol -nr 10 -function GetSystemInstanceList

HANA プライマリがダウンしていることを確認してから続行してください！

3. On the HANA secondary master nameserver (e.g. node21)

# su - sleadm
~> hdbnsutil -sr_takeover
~> cdpy; python3 ./systemReplicationStatus.py; echo RC:$?
~> cdpy; python3 ./landscapeHostConfiguration.py; echo RC:$?
すべて問題がなければ、続行します。

4. 以前の HANA プライマリ マスター ネームサーバー、現在の将来のセカンダリ マスター ネームサーバー (例: node11)

~> hdbnsutil -sr_register --remoteHost=node21 --remoteInstance=10 --replicationMode=sync --name=site2 --operationMode=logreplay
~> sapcontrol -nr 10 -function StartSystem HDB
~> exit

5. 新しいHANAプライマリマスターネームサーバー（例：node21）


~> cdpy; python3 ./systemReplicationStatus.py; echo RC:$?
~> cdpy; python3 ./landscapeHostConfiguration.py; echo RC:$?
~> exit
すべて問題がなければ、続行します。

6. 両方のノードで実行


# cs_clusterstate -i
# crm resource refresh mst_SAPHanaCon_SLE_HDB10
# crm resource maintenance mst_SAPHanaCon_SLE_HDB10 off
# SAPHanaSR-showAttr
# crm_mon -1r
# cs_clusterstate -i

* SAP ツールを使用した SAP HANA のテイクオーバーとプライマリ一時停止機能の概要。

この手順はスケールアップとスケールアウトの両方に有効です。SAP HANAデータベース、システムレプリケーション、Linuxクラスタのステータスを確認する必要があります。SAP HANAリソースをメンテナンスモードに設定し、プライマリをサスペンドしてsr_takeoverを実行し、古いプライマリを新しいセカンダリとして登録します。そのため、正しいセカンダリサイト名を使用する必要があります。最後に、SAP HANAリソースをLinuxクラスタに戻します。以下の「要件」セクションと、後述の正しいサイト名の決定例も参照してください。

1. Linux クラスターと HANA のステータスを確認し、現在のサイト名を表示します。
2. SAPHanaController マルチステートリソースをメンテナンスモードに設定します。
3. テイクオーバーを実行します。プライマリノードのサスペンド機能を使用してください。

~> hdbnsutil -sr_takeover --suspendPrimary

4. 新しいプライマリが動作しているかどうかを確認します。
5. 一時停止中の古いプライマリを停止します。
6. 古いプライマリを新しいセカンダリとして登録します。正しいサイト名を使用していることを確認してください。
7. 新しいセカンダリを起動します。
8. 新しいセカンダリとそのシステムレプリケーションを確認します。
9. SAPHanaController マルチステートリソースを更新します。
10. SAPHanaController マルチステートリソースを管理対象に設定します。
11. 最後に、Linux クラスターと HANA のステータスを確認します。

* Linux クラスターに認識されている 2 つのサイト名を確認します。

これは、AUTOMATED_REGISTER がまだ設定されていない場合に便利です。その場合、以前のプライマリを、以前のサイト名で新しいセカンダリとして手動で登録する必要があります。ポイントは、Linux クラスターで既に使用されているサイト名を見つけることです。新しいセカンダリの登録には、その正確なサイト名を使用する必要があります。SAPHanaSR(7) および SAPHanaSR-ScaleOut(7) の要件も参照してください。
この例では、登録する将来のセカンダリサイトのノードは suse11 です。リモート HANA マスターネームサーバーは、現在のプライマリサイトの suse21 です。小文字の SID は ha1 です。

# crm configure show suse11 suse21
# crm configure show SAPHanaSR | grep hana_ha1_site_mns
# ssh suse21
# su - ha1adm -c "hdbnsutil -sr_state; echo rc: $?"
# exit

* 利用可能なサイトが 1 つしかない場合は、HANA プライマリを手動で起動してください。

クラスターが両方のサイトのステータスを検出できない場合に、この操作が必要になることがあります。これは高度なタスクです。

この操作を行う前に、もう一方のサイトで HANA がプライマリになっていないことを確認してください。

1. 残りのノードでクラスターを起動します。
2. クラスターが実行中であり、ステータスがアイドル状態であることを確認します。
3. sidadm になり、HANA を手動で起動します。
4. HANA が実行中であることを確認します。
5. クラスターが HANA をプライマリに昇格しない場合は、IP アドレスをそのノードに移行するようにクラスターに指示します。
6. クラスターによって HANA がプライマリに昇格されたことを確認し、待機します。
7. IP アドレスから移行ルールを削除します。
8. クラスターがアイドル状態であることを確認します。
9. これで完了です。
10. 他のノードを戻して、できるだけ早く HANA を登録してください。HANA プライマリが長時間放置されると、ログ領域がいっぱいになります。

* ノードがフェンスされた後に Linux クラスターを起動します。

Linux クラスターは、起動時に常に自動的に起動するように設定しないことをお勧めします。クラスターまたはノードが正常に停止した場合にのみ自動的に起動するように設定することをお勧めします。ノードが STONITH によって再起動された場合、クラスターは自動的に起動しません。クラスターがそのように構成されている場合、ノードが STONITH によって再起動された後にクラスターを起動するには、いくつかの手順が必要です。この例では、SBD 経由の STONITH を使用しています。

# cs_clear_sbd_devices --all
# cs_show_sbd_devices
# crm cluster start
# crm_mon -r

* Linux のメンテナンス手順の概要（HANA は Pacemaker-2.0 上で稼働中）

各手順が完了するまで待機し、結果を確認する必要があります。また、本番環境に適用する前に、手順全体をテストし、文書化する必要があります。以下の「要件」セクションと、上記の HANA とクラスターのステータス確認例も参照してください。

1. Linux クラスターと HANA のステータスを確認します（上記を参照）。
2. HANA マルチステート リソースをメンテナンス モードに設定します。

# crm resource maintenance mst_... on

3. いずれかのノードで、Linux クラスターをメンテナンス モードに設定します。

# crm maintenance on

4. すべてのノードでLinux Clusterを停止します。すべてのノードで必ず実行してください。

# crm cluster run "crm cluster stop"

5. Linux のメンテナンスを実行します。

6. すべてのノードで Linux クラスターを起動します。すべてのノードで必ず実行してください。

# crm cluster run "crm cluster start"

7. いずれかのノードでクラスターを操作可能な状態に設定します。

# crm maintenance off

8. Linux クラスターがいずれかのノードで HANA マルチステート リソースのステータスを検出できるようにします。

# crm resource refresh mst_...

9. いずれかのノードで、HANA マルチステート リソースを操作可能に設定します。

# crm maintenance mst_... off

10. Linux クラスターと HANA のステータスを確認します (上記を参照)。

* Linux クラスターを停止し、一時的に無効化するための簡単な手順の概要。HANA は完全に停止します。

この手順は、HANA、OS、またはハードウェアを更新するために使用できます。HANA のロールとリソースのステータスは変更されません。各ステップが完了するまで待機し、結果を確認する必要があります。また、本番環境に適用する前に、手順全体をテストし、文書化する必要があります。

1. HANAプライマリでPacemakerを無効にする
2. HANAセカンダリでPacemakerを無効にする
3. HANAセカンダリでクラスターを停止する

- HANA セカンダリが停止します
- システムレプリケーションがSFAILになる

4. HANAプライマリのクラスタを停止する

- HANA プライマリが停止されます

5. OS またはハードウェアで何らかの操作を行う
6. HANA プライマリで Pacemaker を有効にする
7. HANA セカンダリで Pacemaker を有効にする
8. HANA プライマリでクラスターを起動する

- HANAはダウンしたまま

9. HANAセカンダリ上のクラスタを起動する

- HANA プライマリとセカンダリが起動します
- システムレプリケーションが SOK に回復します

注: ステップ 4 からステップ 9 までは HANA は使用できません。

* SAPHanaSR-angi パッケージの更新手順の概要

この手順は、HANA と Linux クラスターがオンラインのまま、RA、HANA HADR プロバイダーのフックスクリプト、および関連ツールを更新するために使用できます。HANA HADR プロバイダーの再ロードの詳細については、SAPHanaSR-manageAttr(8) も参照してください。

1. Linux クラスターと HANA のステータスを確認します（上記を参照）。
2. リソース SAPHanaController と SAPHanaTopology をメンテナンスに設定します。
3. すべてのクラスターノードで RPM を更新します。
4. 両方のサイトで HANA HADR プロバイダーのフックスクリプトを再ロードします。
5. リソース SAPHanaController と SAPHanaTopology を更新します。
6. リソース SAPHanaController と SAPHanaTopology をメンテナンスから管理対象に設定します。
7. Linux クラスターと HANA のステータスを確認します（上記を参照）。

* Linux クラスター全体から、残っているメンテナンス属性を削除します。

これは、異なるメンテナンス手順による混乱を避けるために行うことができます。稼働中の Linux クラスターでのメンテナンス手順については、上記の概要を参照してください。これを行う前に、クラスター属性 maintenance-mode="false" を確認してください。

# SAPHanaSR-showAttr
# crm_attribute --query -t crm_config -n maintenance-mode
# crm_attribute --delete -t crm_config -n maintenance-mode
# SAPHanaSR-showAttr

* Linux クラスターノードから、残っているスタンバイ属性を削除します。

これは、異なるメンテナンス手順による混乱を避けるために実行できます。稼働中の Linux クラスターでのメンテナンス手順については、上記の概要を参照してください。すべてのノードでこの操作を実行する前に、すべてのノードでノード属性が standby="off" になっていることを確認してください。

# SAPHanaSR-showAttr
# crm_attribute --query -t nodes -N node1 -n standby
# crm_attribute --delete -t nodes -N node1 -n standby
# SAPHanaSR-showAttr

* リソースから残っているメンテナンス属性を削除します。

通常、これは不要です。稼働中のLinuxクラスターでのメンテナンス手順については、上記の概要を参照してください。

# SAPHanaSR-showAttr
# crm_resource --resource cln_SAPHanaTop_HA1_HDB00 --delete-parameter maintenance --meta
# SAPHanaSR-showAttr

* グローバル サイト属性を手動で更新します。

稀に、テイクオーバーが成功した後、他のすべての属性は正しく更新されているにもかかわらず、グローバルサイト属性 hana__glob_prim または hana__glob_sec が自動的に更新されないことがあります。Linux クラスターがしばらくアイドル状態になった後も、グローバルサイト属性は古いままです。この場合、そのサイト属性は手動で更新できます。他のすべての属性に問題がなく、グローバルサイト属性のみが更新されていないことを確認してください。サイト名 VOLKACH の SID HA1 の hana__glob_sec を更新しています。

# crm configure show SAPHanaSR
# crm_attribute --type crm_config --set-name SAPHanaSR --name hana_ha1_glob_sec --update VOLKACH
# crm configure show SAPHanaSR

* スケールアウト srHook 属性を旧スタイルからマルチターゲットにアップグレードします。

このアップグレードの最終結果として、RA とフックスクリプトが旧スタイルからマルチターゲットにアップグレードされます。さらに、Linux クラスターの旧スタイルのグローバル srHook 属性 hana_${sid}_glob_srHook は、サイト対応属性 hana_${sid}_site_srHook_${SITE} に置き換えられます。新しい補助属性が導入されます。手順全体と関連要件については、マニュアルページ SAPHanaSR-manageAttr(8) で詳しく説明されています。
手順の概要:

a. 最初に、すべてが正常に動作しているかどうかを確認します。
b. Linux クラスターリソースの SAPHanaController と SAPHanaTopology をメンテナンスモードに設定します。
c. すべてのノードにマルチターゲット対応の SAPHanaSR-ScaleOut パッケージをインストールします。
d. すべてのノードで sudoers 権限を適用します。
e. 両サイトで HANA HADR プロバイダーの設定を置き換えます。
f. 両サイトで HANA HADR プロバイダーのフックスクリプトを再読み込みします。
g. Linux クラスターと HANA HADR プロバイダーが、定義済みのアップグレードエントリ状態と一致していることを確認します。
h. srHook 属性を旧スタイルからマルチターゲットに移行します。
i. Linux クラスターが、定義済みのアップグレードターゲット状態と一致していることを確認します。
j. Linux クラスターリソースの SAPHanaController と SAPHanaTopology をメンテナンスモードから管理対象モードに設定します。
k. 必要に応じて、Linux クラスター外部のシステムレプリケーションを介して 3 番目の HANA サイトを接続します。
l.最後に、すべてが正常かどうかを確認します。

REQUIREMENTS


* ソフトウェアパッケージ SAPHanaSR-angi に付属するリソースエージェントの現在のバージョンでは、サポートはそれぞれのマニュアルページ SAPHanaSR-angi(7)、SAPHanaSR(7)、および SAPHanaSR-ScaleOut(7) に記載されているシナリオとパラメータに限定されます。

* しばらくお待ちください。Linux クラスターは、HANA の全体的なステータスを検出するために、HANA と設定された間隔およびタイムアウトに応じて、一定の時間を必要とします。

* 何かを行う前に、Linux クラスターのアイドル状態、残っている移行制約、リソース障害、HANA ランドスケープのステータス、および HANA SR のステータスを必ず確認してください。

* クラスター、ノード、およびリソースのメンテナンス属性を混在させることはできません。

* HA/DR プロバイダーイベントを CIB 属性に書き込むには、Linux クラスターが起動して実行されている必要があります。 Linux クラスタのメンテナンス後、現在の HANA SR ステータスは CIB srHook 属性と異なる場合があります。

* Linux クラスタ外での HANA プライマリの起動やテイクオーバーなど、HANA プライマリを手動でアクティブ化すると、プライマリ重複のリスクが生じます。特に HANA プライマリをアクティブ化する場合は、データの整合性についてユーザーが責任を負います。susTkOver.py(7) も参照してください。

* Linux クラスタによって制御される HANA システムレプリケーションを手動で無効化または登録解除する場合は、SAPHanaController リソースをメンテナンスモードにする必要があります。データの整合性についてユーザーが責任を負います。

* HANA サイト名は、RA が最初にアクティブ化されたときに自動的に検出されます。その後のすべての手動タスクでは、その正確なサイト名を使用する必要があります。

* HANA の実行中にクラスタまたは OS をシャットダウンするだけでは、有効なメンテナンス手順とは言えません。これは、特にスケールアウト クラスターでは望ましくない結果をもたらすことが知られています。
