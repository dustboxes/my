14 Nov 2024

NAME

SAPHanaSR_basic_cluster - SAP HANAシステムレプリケーションスケールアップ基本クラスター構成。

DESCRIPTION

SAP HANAシステムレプリケーションのスケールアップシナリオでは、特定の基本的なクラスター構成が必要です。これらの必要な設定に加えて、特定のニーズに対応する追加の設定がいくつかあります。いくつかのSAP HANA設定を適用することも有益な場合があります。

* CRM Basics

default-resource-stickiness = 1000

crmの基本パラメータdefault-resource-stickinessは、リソースが現在実行されているノード上で取得する「stickiness」スコアを定義します。これにより、クラスターの移行中に緊急の必要がない限り、クラスターがリソースを移動することがなくなります。正しい値は、リソースの数、コロケーションルール、およびリソースグループによって異なります。特に、HANAプライマリマスターリソースに併置された追加のグループは、クラスターの決定に影響を与える可能性があります。値が高すぎると、不要なアクションだけでなく、有用なアクションも妨げられる可能性があります。これは、SAPHanaSRが内部スコアリングテーブルを使用して、HANAロールを適切なノードに配置するためです。
Mandatory, default 1.

failure-timeout = 86400

crm基本パラメータfailure-timeoutは、失敗したアクションをCIBに保持する時間を定義します。その後、障害レコードは削除されます。時間は秒単位で測定されます。後述のmigration-thresholdも参照してください。
Optional, no default.

migration-threshold = 5000

crm基本パラメータmigration-thresholdは、リソースが別のノードに移行される前に検出できるリソースのエラー数を定義します。 See also failure-timeout.
Mandatory, default 3.

record-pending = true

op_default record-pendingは、リソースに対するアクションの意図をクラスタ情報ベース (CIB) に記録するかどうかを定義します。このパラメータを「true」に設定すると、crm_mon and Hawkで「starting」や「stopping」などの保留中のアクションを表示できます。
Optional, default false.

pcmk_delay_max = 30

sbd stonithパラメータpcmk_delay_maxは、フェンシング/stonith要求がトリガーされるまでの待機の上限を定義します。このパラメーターは、spill-brainの場合にクラスターが不要な二重フェンスを防ぐ必要があります。優先フェンシングが使用される場合を除き、30秒前後の値が必要です。
Mandatory, default 5.

priority-fencing-delay = 30

オプションのcrmプロパティpriority-fencing-delayは、クラスタパーティション内のノードの大部分が存在しない場合に、合計リソースの優先度が最も高い失われたノードを対象とするフェンシングの遅延を指定します。これにより、より重要なノードがフェンシングの一致に勝つ可能性があります。これは、2ノードクラスターのスプリットブレインで特に意味があります。基本優先度が0でない場合、プロモートされたリソースインスタンスは計算時に基本優先度+1を取得します。対応するフェンシングリソースに対して設定されたpcmk_delay_maxによって導入された遅延は、この遅延に追加されます。これを機能させるには、SAPHanaControllerプリミティブリソースのmeta属性priority=100または同様の値が必要です。ocf_suse_SAPHanaController (7) を参照ください。遅延はpcmk_delay_maxよりかなり大きいか、安全に2倍でなければなりません。
Optional, no default.

* systemd Basics

saphostagent.service enabled
SAP${SID}_${INO}.service enabled

HANAデータベースにsystemdスタイルのinitを使用する場合、サービスsaphostagentとSAP${SID}_${INO}を有効にし、SAPスライス内で実行する必要があります。インスタンスプロファイルの自動開始機能をオフにする必要があります。サービスsaptuneを強く推奨します。saptune (8) のマニュアルページを参照してください。

* pacemaker service dependency to SAP instance service

[Unit]
Wants=SAP${SID}_${INO}.service
After=SAP${SID}_${INO}.service

In case systemd-style init is used for the HANA database, it might be desired to have the SAP instance service stopping after pacemaker at system shutdown. Therefor a drop-in file for the pacemaker service might help. See examples below.

* pacemaker service basics

PCMK_fail_fast = yes

HANAデータベースにsystemdスタイルのinitが使用されている場合は、システムのシャットダウン時にペースメーカーの後でSAPインスタンスサービスを停止することが望ましい場合があります。そのため、ペースメーカーサービス用のドロップインファイルが役に立つかもしれません。以下の例を参照してください。
Optional, default no.

* SAP HANA Basics

/usr/sap/${SID}/SYS/global/hdb/custom/config/global.ini

[memorymanager]
final_memory_release_shutdown = [ auto | on | off ]
final_memory_release_crash = [ auto | on | off ]

Starting with SAP HANA 2.0 SPS06, the database shutdown can be accelerated by optimizing memory de-allocation. Please refer to SAP documentation before setting this parameters.

/usr/sap/${SID}/SYS/global/hdb/custom/config/daemon.ini

[daemon]
terminationtimeout = [ millisec ]
forcedterminationtimeout = [ millisec ]

最初のパラメーターは、STOPイベントによってHANAがシャットダウンされるときに、SIGTERMを送信してから最終的に子プロセスを終了するまでのタイムアウトを定義します。'restartterminationtimeout'パラメータが設定されていない場合、システム再起動の最大遅延としても使用されます。2つ目は、QUITイベントによってHANAがシャットダウンされるときに、SIGTERMを送信してから最終的に子プロセスを終了するまでのタイムアウトを定義します。このパラメータを設定する前に、SAPのマニュアルを参照してください。

EXAMPLES

* crm basic configuration

SAPHanaSRのcrm基本設定の例を次に示します。必要な特定のパラメータを示します。一部の一般パラメータは省略されています。

The following example is for 15 SP5 with disk-based SBD:


property cib-bootstrap-options: \
have-watchdog=true \
cluster-infrastructure=corosync \
cluster-name=hacluster \
stonith-enabled=true \
placement-strategy=balanced \
stonith-timeout=144 \
rsc_defaults rsc-options: \
resource-stickiness=1000 \
migration-threshold=3 \
failure-timeout=86400
op_defaults op-options: \
timeout=600 \
record-pending=true

* crm simple SBD stonith configuration

SBDのセットアップを完了するには、CIBでSTONITH/フェンシングメカニズムとしてSBDをアクティブにする必要があります。SBDは通常、SAPHanaSRスケールアップのために他のフェンシング/石化機構の代わりに使用される。ベーシック・ディスク・ベースのSBDリソースの例:

primitive rsc_stonith_sbd stonith:external/sbd \
params pcmk-delay-max=30

* crm priority fencing SBD stonith configuration

Example for a priority fencing disk-based SBD resource.


primitive rsc_stonith_sbd stonith:external/sbd \
params pcmk-delay-max=15 \
property cib-bootstrap-options: \
priority-fencing-delay=30

* crm simple IP address resource configuration

Linuxクラスターで1つのIPアドレスを管理し、そのアドレスをHANAプライマリマスターネームサーバーと共に移動します。間隔とタイムアウトは、フレンドリ条件に設定されます。


primitive rsc_ip_SLE_HDB00 IPaddr2 \
op monitor interval=10 timeout=20 \
params ip=192.168.178.188
colocation col_ip_with_SLE_HDB00 \
2000: rsc_ip_SLE_HDB00:Started mst_SAPHanaCon_SLE_HDB00:Promoted

* crm protective IP address resource configuration

Linuxクラスタに1つのIPアドレスを管理させます。リソースは、(仮想) ネットワークカードの短い不在を許容する必要があります。モニターとその結果の起動が失敗した場合、ノードはフェンスされます。これにより、HANAデュアルプライマリのリスクから保護されます。このIPアドレスリソースとHANAプライマリマスターネームサーバー間のコロケーション制約も必要です。それぞれの例を参照してください。


primitive rsc_ip_SLE_HDB00 IPaddr2 \
op monitor interval=30 timeout=60 \
op start timeout=90 on-fail=fence \
params ip=192.168.178.188 cidr_netmask=32

この構成は、仮想NICが一時的に消失する可能性があるパブリッククラウド環境で使用される場合があります。もちろん、本番環境でNICが消失しないようにすることをお勧めします。すなわち。ネットワークに冗長性を追加するか、クラスタをメンテナンス状態に設定します。

* crm IP address for active/active read-enabled resource configuration

Linuxクラスターで追加のIPアドレスを管理し、そのアドレスをHANAセカンダリマスターネームサーバーと共に移動します。


primitive rsc_ip_ro_SLE_HDB00 IPaddr2 \
op monitor interval=10 timeout=20 \
params ip=192.168.178.199
colocation col_ip_ro_with_secondary_SLE_HDB00 \
2000: rsc_ip_ro_SLE_HDB00:Started mst_SAPHanaCon_SLE_HDB00:Demoted
location loc_ip_ro_not_master_SLE_HDB00 \
rsc_ip_ro_SLE_HDB00 \
rule -inf: hana_sle_roles ne master1:master:worker:master

* crm grouped IP address resource configuration

Linuxクラスターで1つのIPアドレスを管理し、そのアドレスをHANAプライマリマスターネームサーバーと共に移動します。特定のパブリッククラウドの目的には、補助リソースが必要です。

リソースをHANAマスターロールにバインドしないでください。これにより、有効なリソーススコアリングが変更され、クラスターが期待どおりのアクションを実行できなくなる可能性があります。何らかの理由で追加のリソースをHANAリソースにバインドする必要がある場合は、その追加リソースの固定性を1に減らす必要があります。


primitive rsc_ip_SLE_HDB00 IPaddr2 \
op monitor interval=10s timeout=20s \
params ip=192.168.178.188 cidr_netmask=32
primitive rsc_lb_SLE_HDB00 azure-lb \
params port=62502
group grp_ip_SLE_HDB00 rsc_lb_SLE_HDB00 rsc_ip_SLE_HDB00 \
meta resource-stickiness=1
colocation col_ip_with_SLE_HDB00 \
8000: grp_ip_SLE_HDB00:Started mst_SAPHanaCon_SLE_HDB00:Promoted

* crm MailTo resource configuration

HANAランドスケープの状態は、属性hana__rolesとしてCIB内に格納されます。正常なHANAマスターは、"master1:master:worker:master"のようになります。最初のフィールドはHANAランドスケープの状態です。この状態が3または2になった場合、HANAに何かが発生していますが、クラスターはテイクオーバーを実行しません。ステータス1はテイクオーバーをトリガーし、ステータス0は未定義の致命的エラーを示します。マニュアルページocf_suse_SAPHanaController (7) およびocf_heartbeat_MailTo (7) を参照してください。

属性hana__rolesが上記の理想から逸脱するとすぐに通知するMailToリソースを定義できます。

primitive rsc_mailto_HA1_HDB10 MailTo \
params email="root@localhost" subject="hana_ha1_roles changed" \
op monitor timeout=10 interval=30 depth=0 \
location loc_mailto_HA1_HDB10_with_sane rsc_mailto_HA1_HDB10 \
rule 90000: hana_ha1_roles eq master1:master:worker:master
colocation col_mailto_HA1_HDB10_with_prim \
3000: rsc_mailto_HA1_HDB10:Started mst_SAPHanaCon_HA1_HDB10:Promoted

* check how resource stickiness affects promotion scoring

SAPHanaSRは、内部スコアリングテーブルを使用します。HANAプライマリマスターとセカンダリマスターの昇格スコアは一定の範囲にあります。Linuxクラスターで使用されるスコアは、同じ範囲にある必要があります。


# SAPHanaSR-showAttr | grep master.:master
# crm_simulate -Ls | grep promotion

* clean up SDB stonith resource after write failure

Iまれに、SBD stonithリソースがブロックデバイスへの書き込みに失敗することがあります。根本原因が見つかって修正されたら、エラーメッセージを消去できます。


# stonith_admin --cleanup --history=<originator_node>

* check saphostagent and show SAP instances

Basic check for the saphostagent.

# /usr/sap/hostctrl/exe/saphostctrl -function Ping
# /usr/sap/hostctrl/exe/saphostctrl -function ListInstances

* check systemd services for the HANA database

HANAデータベースにsystemdスタイルのinitが使用されている場合は、サービスを確認できます。例SIDはHA1、インスタンス番号は10です。


# systemctl list-unit-files | grep -i sap
# systemctl status SAPHA1_10.service
# systemd-cgls -u SAP.slice
# systemd-cgls -u SAPHA1_10.service
# systemctl show SAPHA1_10.service

* show pacemaker service drop-in file

HANAデータベースにsystemdスタイルのinitが使用されている場合は、システムのシャットダウン時にペースメーカーの後でSAPインスタンスサービスを停止することが望ましい場合があります。ドロップインファイルが役に立つかもしれません。例SIDはS07、インスタンス番号は00です。

# cat /etc/systemd/system/pacemaker.service.d/00-pacemaker.conf
[Unit]
Description=pacemaker needs SAP instance service
Documentation=man:SAPHanaSR_basic_cluster(7)
Wants=SAPS07_00.service
After=SAPS07_00.service

* check for pacemaker dependency to SAP instance service

Example SID is S07, instance number is 00.

# systemctl show pacemaker.service | grep SAPS07_00
# systemd-delta | grep pacemaker
# systemd-analyze dot | grep "pacemaker.*SAPS07_00"
